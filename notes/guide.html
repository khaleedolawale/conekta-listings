1. Big picture

Three files, three jobs:

  • index.html is the structure and the content: what is on the page.
  • style.css is the presentation: how it looks and how it rearranges on different screens.
  • script.js is the behaviour: it makes the search box and filter chips actually hide and show cards.

The cards are written directly in the HTML (not generated by JavaScript). Each card carries its facts in data-* attributes. JavaScript only reads those and hides or shows cards. Benefit: the page still shows all properties even if JavaScript fails to load, and the structure is easy for screen readers and search engines.

One-line summary for the interview: "Static semantic HTML for content, mobile-first CSS Grid for layout, and a small amount of vanilla JavaScript that filters by toggling the hidden attribute."

3. Anatomy of one property card

<li class="listing" data-location="lekki" data-price="4500000" data-bedrooms="2">
  <article class="card">
    <div class="card-media">
      <div class="card-image" role="img" aria-label="...">...</div>
      <span class="badge">Verified</span>
    </div>
    <div class="card-body">
      <h3 class="card-title">...</h3>
      <p class="card-area">...</p>
      <p class="card-meta">...</p>
      <p class="card-price">...</p>
      <button class="btn btn-details">View details</button>
    </div>
  </article>
</li>
  • li with data attributes: data-location, data-price (plain number, no commas or symbol) and data-bedrooms are what the filters compare against. Numbers must be clean so JavaScript can do maths on them.
  • article: one self-contained item (a property) that would make sense on its own. That is exactly what article is for.
  • card-media: a wrapper with position: relative so the badge can sit on top of the image corner.
  • card-image: the image placeholder. It is a div with role="img" and an aria-label because it is not a real image yet. When real photos arrive, swap it for an <img> with proper alt text.
  • badge: the word "Verified" is real text, so it does not rely on colour or an icon alone. The check mark is aria-hidden so it is not read out twice.
  • h3: the card title. It sits under the hidden h2 "Properties".
  • card-price: the price per year in Naira. The visually hidden "Price:" gives screen readers context. The unit "per year" is smaller and greyer.
  • View details button: an aria-label that starts with the visible text and adds the property name. Without it, a screen reader user would hear "View details, button" twelve times with no idea which is which.

4. CSS: variables, reset and utilities

:root custom properties

Variables like --primary and --border are defined once and reused with var(--primary). To change the brand colour, change one line. All colour pairs were picked for strong contrast: dark text on white, and white text on the dark green.

The reset

  • box-sizing: border-box makes padding and border count inside the width. Stops elements overflowing their containers.
  • body sets the font stack (system fonts load instantly, no downloads), background, text colour and a comfortable line-height: 1.5.
  • Margins on headings and paragraphs are zeroed so spacing is controlled deliberately with gap and padding.
  • [hidden] { display: none !important; } guarantees the hidden attribute always wins, even if another rule sets a display value. Filtering depends on it.

:focus-visible

A thick blue outline with a small offset, shown only when navigating by keyboard. This is the main keyboard-navigation requirement, and I never use outline: none without a replacement.

.container

max-width: 1200px plus margin-inline: auto centres the content. Side padding stops text touching the screen edge on phones.

.visually-hidden

Hides something visually but keeps it available to screen readers. Not the same as display: none, which hides it from everyone.

.skip-link

Positioned off screen (top: -100%). On focus it moves to top: 1rem, so it appears only when a keyboard user reaches it.

5. CSS: header and search bar

  • .site-header: position: sticky; top: 0 keeps the search at the top while scrolling. Good for users in a hurry on phones. z-index keeps it above the cards.
  • .header-inner: on mobile, a column (brand above search). From 768px it becomes a row.
  • .search: a flex row. The input gets flex: 1 so it takes all spare space and the button stays its natural size. min-width: 0 lets the input shrink instead of overflowing on very narrow screens.
  • min-height: 44px on inputs and buttons: the recommended minimum touch target size, so thumbs do not miss.
  • .btn: shared button style (colour, radius, hover). .btn-details and .btn-search are only hooks for specific tweaks.

6. CSS: filter chips

  • .filters: a grid with a gap, so each filter group stacks with consistent spacing.
  • .chips: a flex row. On mobile it scrolls sideways (overflow-x: auto) so three filter rows stay compact and do not push the listings far down. From 768px it wraps instead.
  • The padding: 4px; margin: -4px trick leaves room for the focus outline, otherwise the scroll container would clip it.
  • .chip: pill shape (border-radius: 999px), flex: 0 0 auto so chips never squash, 44px min height.
  • .chip[aria-pressed="true"]: the selected style is driven by the same attribute screen readers use. Visual state and accessibility state can never go out of sync. The selected chip also gets bold text, so it is not distinguished by colour alone.

7. CSS: the property card

  • .card: display: flex; flex-direction: column; height: 100%. Every card stretches to the row height, and the button is pushed to the bottom even when titles wrap to different lengths.
  • .btn-details uses margin-top: auto for that push. That is the flexbox "fill the spare space above me" trick.
  • .card-image: aspect-ratio: 16 / 10 keeps the image area the same shape at every width. display: grid; place-items: center centres the placeholder text.
  • :nth-child(3n + 2) and (3n + 3): give the placeholders three different gradients so the grid does not look flat.
  • .badge: absolutely positioned inside .card-media (top left). White background with dark green text for strong contrast on any gradient.
  • .card-price: biggest and boldest text on the card, because price is what people scan for first.
  • :hover lift and shadow: small polish. prefers-reduced-motion removes the movement for people who ask their system for less animation.

8. CSS: mobile-first grid and breakpoints

.grid { display: grid; grid-template-columns: 1fr; gap: 1rem; }

@media (min-width: 768px)  { .grid { grid-template-columns: repeat(2, 1fr); } }
@media (min-width: 1200px) { .grid { grid-template-columns: repeat(3, 1fr); } }
  • Mobile-first means the base CSS (outside any media query) is the phone layout: one column. Bigger screens add rules with min-width. We only add complexity as screens get bigger.
  • 1fr means "one share of the free space". repeat(2, 1fr) is shorthand for two equal columns.
  • 768px is where the spec asks for 2 columns (tablet and up). 1200px is where it asks for 3 (desktop).
  • Inside the 768px query I also switch the header to a row, let the chips wrap, and increase the page gutter. Anything that changes at a breakpoint lives inside that breakpoint.
  • Why Grid and not Flexbox for the cards? Grid controls rows and columns together, so all cards in a row line up and share equal widths. Flexbox is better for one-dimensional layouts like the search row and the chip rows.
  • Hidden cards (display: none) drop out of the grid, and the remaining cards reflow automatically. No extra code is needed.

9. JavaScript: how filtering works

The whole script is wrapped in (() => { ... })();, an immediately invoked function. That keeps variables private and out of the global scope.

state

One object remembering the current choices: { query, location, price, bedrooms }. Each starts as 'all' (or empty for the query). Having one source of truth means the screen is always a function of that state.

Element lookups

getElementById and querySelectorAll grab the form, the input, the chips, the cards, the counter, the empty state and the reset button once, at the top. Array.from turns the NodeList of cards into a real array so array methods work.

priceRules

An object that maps a price filter key to a small test function. under is below 1,500,000, mid is 1,500,000 to 3,000,000 inclusive, and over is above 3,000,000. This replaces a long if-else chain, and adding a new price band is one new line.

matchesBedrooms(bedrooms, selected)

Returns true for "all", uses greater-than-or-equal for "4" (which means 4+), otherwise checks exact equality. Number() is needed because dataset values are always strings.

matchesQuery(listing)

Takes the card's visible text, lowercases it, splits the search into words, and requires every word to appear somewhere. So "2 bedroom lekki" works even though the words are in different places on the card.

matchesFilters(listing)

Combines everything with &&. A card shows only if the search, location, price and bedroom checks all pass. Destructuring const { location, price, bedrooms } = listing.dataset pulls the data attributes out in one line.

render()

Loops through every card, sets listing.hidden to the opposite of the match result, and counts visible ones. Then it updates the "N properties found" text (handling singular versus plural) and shows or hides the empty state. It is the only function that touches the visibility of cards.

selectChip(filter, value)

Saves the value in state and loops over the chips of that filter group only, setting aria-pressed to true on the chosen one and false on the rest. Converting to a string is needed because attributes hold text.

updateQuery()

Reads the input, trims spaces, lowercases it, stores it in state, and calls render. Used for both typing and submitting.

resetAll()

Clears the search, sets every filter back to "all", re-renders, and moves focus back to the search input so keyboard users are not left on a button that just disappeared.

Event listeners

  • Chips: each chip listens for a click, calls selectChip, then render.
  • Input event: filters live as the user types.
  • Form submit: event.preventDefault() stops the page reloading, then filters. This makes the Enter key and the Search button work.
  • Reset button: calls resetAll.

The final render() call at the bottom runs once at load so the count is correct from the start.

If asked what I would improve: debounce the search input, store filters in the URL so results are shareable, and load listings from an API instead of static HTML.

10. Accessibility choices

  • Semantic landmarks: header, main, footer, sections and a search form.
  • Labels: the search input has a real label tied by for and id. Filter groups are named via aria-labelledby.
  • Keyboard: everything is a native link or button, tab order matches visual order, there is a skip link, and the focus ring is always visible.
  • State: chips use aria-pressed. The result count is a status region so changes are announced.
  • Contrast: text and button colours chosen for strong contrast (white on dark green, dark grey on white). I should still run the page through a contrast checker or Lighthouse to confirm.
  • Not colour alone: the verified badge says "Verified", and the selected chip is bold as well as coloured.
  • Touch targets: at least 44px tall.
  • Reduced motion: transitions are turned off when the user asks for it.
  • Distinct button names: every View details button says which property it is for.

11. Interview questions I should be ready for

Why mobile-first?

The brief says tenants browse on phones in a hurry. Designing the small layout first forces me to keep only what matters, and larger screens just add columns.

Why are the cards in HTML and not generated with JavaScript?

Content works without JavaScript, structure is easier to review, and there is no flash of empty content. For real data I would fetch from an API and render the same markup.

How does the filter combine several choices?

Every card is tested against all four conditions with AND. Within a group only one chip is active, so there is no OR logic to manage.

Why hidden and not removing elements?

It is simple, reversible, keeps DOM order, and hidden elements are removed from the accessibility tree automatically.

Why a button for chips and not a checkbox?

Chips are single-choice toggles that look like buttons. A button with aria-pressed is a good fit. Radio buttons would also be valid.

What would you do with more time?

Real images with lazy loading, a details page, sorting by price, URL-based filters, a debounced search, and automated accessibility tests.

What did AI help with?

Be straight about it: AI helped draft the code and this guide, and I reviewed, tested and understood each part. The README has the exact disclosure.

Before the interview: open the page, break something on purpose (change a breakpoint, rename a data attribute, remove an aria attribute) and fix it. If I can do that, I understand it.

Run locally

Open index.html in a browser, or run python3 -m http.server 8000 in the project folder and visit http://localhost:8000.

Deploy on GitHub Pages

Push to GitHub, open the repository's Settings, then Pages, choose the main branch and root folder, and save. The live link appears after a minute or two. Open the live link on your phone before submitting.
